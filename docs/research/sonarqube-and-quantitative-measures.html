SonarQube and Quantitative Measures

Should SonarQube compute the numbers behind our Verdicts? Every claim here was re-checked against official docs, live APIs or a real run on 2026-11-04.

1. Summary

Recommendation: compute the measures ourselves with small local Python libraries, rate them with the SIG model from Maintainability_Measurement_Models.pdf, and use SonarQube to cross-check our numbers and as a baseline, not as the engine.
  • The SonarQube CLI (sonar) doesn't compute measures. It queries an existing SonarQube project for issues and quality-gate status. Its local analysis is SonarQube Cloud only, and its Agentic Analysis needs a paid plan.
  • SonarQube Server and Community Build compute some measures: cyclomatic and cognitive complexity, duplication, size, debt ratio, plus coverage if you import it. That is per file at the finest; there are no per-function values.
  • SonarQube lacks most of what the PDF needs. SonarCloud's full list of 165 metrics has no MI, Halstead, CK, Martin, fan-in/out or cycle measures. Its lack of per-function values also means it can't build the SIG risk profiles that the PDF picks as the main frame.
  • The local libraries ran on our fixture and produced per-function numbers with file and line. Running them found two things to handle. radon's MI isn't the formula in the PDF: it gives 68.5 on app.py, against 55.9 with the PDF's formula. And grimp needs a real package, so it can't graph loose scripts.

Running it ourselves: Community Build is free and self-hosted, and it ships as the sonarqube Docker image. The docs ask for 4 GB of RAM for a small installation, and an Elasticsearch kernel setting of vm.max_map_count ≥ 524288 on the host. Analysis is asynchronous: you scan, the server processes the report, then you query the API. That is fine for a batch over the evaluation set, but heavy for every Run of a web chat product.

Finding 1: radon's MI isn't the PDF's MI

The PDF uses the Visual Studio formula, MAX(0, (171 − 5.2·ln HV − 0.23·CC − 16.2·ln LOC) × 100 / 171). radon's mi_compute adds + 50·sin(√(2.46·rad(comments))) and caps the result at 100. On app.py:

FormulaInputsMI
radon, with the comment termHV 129.32, CC 7, 20 source lines, 1 comment line68.50
PDF / Visual Studio, no comment termHV 129.32, CC 7, LOC 2055.89

Both fall in the green band (20–100), but the numbers differ by 12.6 points. So we should take HV, CC and LOC from radon and apply the PDF's formula in our own code. The report should then state which formula we used.

Finding 2: grimp needs a package

grimp builds the graph only from an importable package (a folder). Loose scripts that use from utils import …, as the fixture does, produce no edges. Real targets are usually packages, but we need a fallback: a small walker using Python's ast module that resolves imports between files under the target.

Finding 3: the numbers check out by hand

radon and lizard both give process_order a CC of 7, and a hand count of its decision points (if, for, if, if, elif, if, plus 1) also gives 7. Its cognitive complexity of 8 from complexipy matches a hand count too: +1 for each of lines 8, 11, 17 and 20, and +2 for lines 12 and 15, which are nested in the loop. Two tools agreeing with each other and with a hand count is a cheap check that our measurement is right. SonarQube can be a third check, per file.

6. Proposal: three layers

1
Measure, deterministic and local, takes seconds

Per-function, per-file and per-module numbers, each with a file and line, from radon, lizard, complexipy and grimp, plus our own ast walker for CK and imports.

2
Rate, deterministic, no LLM

Apply the PDF's formulas and thresholds (SIG risk profiles, Martin D, duplication bands) and give each Characteristic a rating from ++ to −−. The same code always gets the same rating: this is our own quantitative matrix.

3
Agent, the LLM

The agent reads the numbers through tools, cites the worst units as Evidence, checks what numbers can't see (names, comments), and gives the Verdict. If its Verdict disagrees with the rating, it has to explain why.

The risk profile for moderate / high / very high is 0% / 0% / 0% of lines of code, so the CC rating is ++. The fixture is labelled "deliberately not well-structured", and CC alone doesn't catch that. That is the case for combining several measures and for the agent's layer-3 check.

A new glossary term

GLOSSARY.md lists "metric" as a word to avoid, because it's a synonym for Characteristic. The numbers need their own term. A proposal: Measure, "one number computed from the code, such as the CC of a function, with the file and line it applies to". It should be added before any code is written.

7. Where SonarQube fits

  • Checking our numbers. Run Community Build once over the evaluation projects and compare its per-file CC, cognitive complexity and duplication with ours. Close agreement makes a strong section for the report.
  • A baseline in the evaluation matrix. A "SonarQube rating only" baseline (its A–E rating mapped to pass/fail) against "agent with measures" is a fair comparison for the supervisor.
  • Later, optionally, an adapter so the agent can read a team's existing SonarQube project, through the Web API or the SonarQube MCP Server. It isn't needed now.

Probe: what each tool counts

To explain the CC gap, I scanned 17 tiny files, each a function containing one construct. The table gives the file-level value from each tool.

ConstructCC SonarQubeCC lizardCC radonCognitive SonarQubeCognitive complexipy
plain function11100
if22211
if + elif23322
if + else22222
for, while, and, or, ternary22211
try / except12211
comprehension with if23302
assert11200
match with 2 cases13201
with11100
for + else22321
if at module level, no function10011

What this means: "cyclomatic complexity" is three slightly different measures. SonarQube doesn't count elif, except, comprehension filters or match cases. radon counts assert and loop else. lizard ignores code outside functions. Cognitive complexity agrees on ordinary code but differs on comprehensions, match and loop else. A cross-check therefore can't expect equal totals. It has to explain each gap by one of these rules, and the report has to name the definition we use.

Recommendation: use lizard for CC and unit size. It works per function, which is what SIG risk profiles need, and it counts elif and except as McCabe does. Use complexipy for cognitive complexity. Treat SonarQube's per-file values as a check whose known differences are listed in this table.
