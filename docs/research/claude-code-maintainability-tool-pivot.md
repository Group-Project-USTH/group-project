# Pivot the delivery surface, keep the Measures

Yes, this repo should become a Claude Code tool, on two conditions. First, the owner has to confirm the course does not require DeepAgents or a web UI. Second, the pivot should change how the tool is delivered, not what it is. The fitting form is a **Claude Code plugin that bundles a stdio MCP server for the deterministic Measures and a portable skill holding a rubric for each Characteristic**. A Stop hook and a CI recipe built on `claude -p --json-schema` are optional extras. Every part of this ships from the existing public GitHub repo with two install commands and no review process. The cost of switching is low. The web chat product has only `GET /health` and no frontend. The parts worth keeping, `schemas.py` and `measures/`, already import nothing from the LLM stack. The market is crowded, though. **SonarSource has an official plugin in Anthropic's own marketplace. CodeScene, SIG, Codacy and DeepSource all reach Claude Code through MCP. An unrelated PyPI project already called `maintainability-agent` ships an MCP server and a Claude Code skill with grades it describes as ISO-25010-inspired.** The open gap is narrow: a Verdict (pass/fail/unknown) for each of the five ISO/IEC 25010 maintainability Characteristics, with file and line Evidence anchored in Measures and checked against expert ratings. The research literature has not tested whether giving an LLM computed Measures improves its agreement with experts. Answering that question is the project's defensible contribution, so the plan below builds the evaluation harness *before* deleting the current agent. That way the old agent becomes the first baseline.

## A plugin wrapping an MCP server and a skill is the form that fits

In Claude Code, a plugin is the unit of packaging and distribution, not one option among several. A single directory with an optional `.claude-plugin/plugin.json` can bundle skills, subagents, hooks, MCP servers, LSP servers and a `bin/` of executables. It is published by committing a `.claude-plugin/marketplace.json` to a git repo, and **"Once the file is in the repository, the plugin is published, with no submission form"** ([Publish and distribute a plugin](https://code.claude.com/docs/en/plugins/publish)). Users run `claude plugin marketplace add owner/repo` and then `claude plugin install name@marketplace`. Marketplace sources can be relative paths, GitHub, git subdirectories, URLs, archives, npm or commands. **There is no PyPI source type** ([Create a marketplace](https://code.claude.com/docs/en/plugin-marketplaces)). Python code must therefore either live in the plugin repo or be fetched at run time by `uvx`. Plugin names must not start with `claude-`, `anthropic-` or `cc-plugin-`. `claude plugin validate --strict` is the check to run in CI ([Plugin manifest reference](https://code.claude.com/docs/en/plugins-reference)).

The tool needs three things: deterministic numbers, judgement against a rubric, and a Verdict that can be validated against a schema. Each maps onto a different mechanism. An **MCP server** gives typed, schema-checked tool output that the model cannot alter. Plugin MCP servers start automatically when the plugin is enabled, and the same server also works in VS Code Copilot, Cursor and Cowork ([MCP in Claude Code](https://code.claude.com/docs/en/mcp); [VS Code MCP servers](https://code.visualstudio.com/docs/copilot/customization/mcp-servers)). The official Python SDK is `mcp` 2.3.0 (2026-10-02), whose high-level class is now `MCPServer` ([PyPI mcp](https://pypi.org/pypi/mcp/json); [python-sdk](https://github.com/modelcontextprotocol/python-sdk)). Claude Code warns when tool output passes **10,000 tokens and caps it at 25,000 by default**, so the server has to return compact summaries rather than every function's Measures ([MCP in Claude Code](https://code.claude.com/docs/en/mcp)). A **skill** is the natural home for the rubric. It is plain Markdown that loads only when its description matches. It follows the open Agent Skills standard, which Cursor also reads from `.claude/skills/` ([Cursor skills docs](https://cursor.com/docs/context/skills); [agentskills.io](https://agentskills.io)). Outside Claude Code, however, only six frontmatter fields are allowed, and `!` command injection and `$ARGUMENTS` do not work ([Skills](https://code.claude.com/docs/en/skills)).

The remaining mechanisms are useful but secondary. A **Stop hook** can run the Measures after Claude finishes editing and block on a threshold breach. The hooks documentation itself recommends `PostToolUse` on `Edit|Write` for quick per-file checks and `Stop` for slower project-wide checks ([Hooks](https://code.claude.com/docs/en/hooks)). **Headless mode** puts output that conforms to a JSON schema in `structured_output` and reports `total_cost_usd`. `--bare` skips local discovery so scripted Runs can be reproduced ([Headless](https://code.claude.com/docs/en/headless)). `anthropics/claude-code-action@v1` can install a plugin from a marketplace and invoke one of its skills in CI ([GitHub Actions](https://code.claude.com/docs/en/github-actions)). Two constraints shape the design. Plugin subagents ignore their own `mcpServers` and `hooks` frontmatter "for security reasons", so a reviewer subagent must rely on the plugin's `.mcp.json` ([Subagents](https://code.claude.com/docs/en/sub-agents)). A top-level `bin/` makes claude.ai Chat and Cowork refuse the whole plugin ([Plugin feature support across platforms](https://claude.com/docs/plugins/platform-support)). [Inference] Ship the MCP server and the skill as the core. Leave out `bin/`. Make the hook opt-in. Name the skill anything except `code-review` (which would shadow the bundled one), `verify` or `simplify` (which Claude Code runs before commits).

The built-in features overlap less than their names suggest. **`/code-review` looks for correctness bugs in branch changes.** The managed Code Review service "focuses on correctness: bugs that would break production" and reads code "without building or running your code" ([Review locally](https://code.claude.com/docs/en/code-review-local); [Code Review](https://code.claude.com/docs/en/code-review)). Neither computes Measures or gives a Verdict per Characteristic. The documentation lists "your own reviewer, as a subagent or skill" as a supported option.

## Six incumbents already sit inside Claude Code, but none gives a Verdict per Characteristic

The claim "run static analysis from inside Claude Code" is already taken. On 2026-04-16 SonarSource shipped **an official Claude Code plugin in `claude-plugins-official`**. It bundles skills, agents, a SonarQube MCP server and PostToolUse hooks that analyse every edited file, and it markets this as "deterministic" verification in contrast to LLM self-checking ([Sonar blog](https://www.sonarsource.com/blog/now-available-sonarqube-plugin-for-claude-code)). Sonar's MCP server is source-available under a licence restricted to a "Non-Competitive Purpose" ([About the MCP server](https://docs.sonarsource.com/sonarqube-mcp-server/about-the-mcp-server)). [Inference] That licence makes Sonar suitable as a cross-check, not as a component, which matches the repo's existing decision. The table below summarises where each neighbour stands.

|---|---|---|---|---|
| SonarQube | Official plugin + MCP | A–E rating from a technical-debt ratio, issues, quality gates | None; three "software qualities" | Cloud/Server; agentic analysis needs Cloud |
| CodeScene | Plugin + CodeHealth MCP | Code Health 1–10 per file from 25+ weighted smells | None | €18/author/month Standard |
| SIG Sigrid | Guardrails MCP | Maintainability stars per system property, benchmarked against 40,000+ systems | Explicit, TÜViT-certified | Sales-led |
| Codacy / DeepSource / Qlty | MCP (Codacy, DeepSource); CLI only (Qlty) | A–F or A–D grades from weighted aggregates | None | Free tiers exist |
| `maintainability-agent` (PyPI) | MCP + Claude Code skill | 0–5 per category, letter grade calibrated on 201 repos, no LLM | "Loosely modeled", not certified | Free, MIT |
| `quodeq` | Via Claude Code and other CLIs | LLM 0–10 grades on six top-level ISO 25010 characteristics, file/line findings | Top-level only | Free, MIT |

Sources: [Sonar definitions](https://docs.sonarsource.com/sonarqube-cloud/digging-deeper/metric-definitions), [CodeScene Code Health](https://codescene.io/docs/guides/technical/code-health.html), [CodeScene pricing](https://codescene.com/pricing), [codehealth-mcp](https://github.com/codescene-oss/codehealth-mcp), [SIG MCP](https://www.softwareimprovementgroup.com/mcp/), [SATToSE 2019](https://ceur-ws.org/Vol-2510/sattose2019_paper_11.pdf), [Qlty maintainability docs](https://docs.qlty.sh/cloud/maintainability/metrics), [Codacy docs](https://docs.codacy.com/faq/code-analysis/which-metrics-does-codacy-calculate/), [DeepSource MCP](https://deepsource.com/docs/developers/mcp), [PyPI maintainability-agent](https://pypi.org/project/maintainability-agent/), [quodeq](https://github.com/quodeq/quodeq).

Two of these rows matter most for this repo. **SIG** is the only commercial model built explicitly on ISO 25010. It maps volume, duplication, unit size, unit complexity, unit interfacing, module coupling, component balance and component independence onto the five Characteristics. The mapping is "based on expert opinion", and star ratings come from a proprietary benchmark ([SATToSE 2019](https://ceur-ws.org/Vol-2510/sattose2019_paper_11.pdf)). SIG's MCP page does not mention ISO 25010 or stars, so it is unclear what the agent actually receives ([SIG MCP](https://www.softwareimprovementgroup.com/mcp/)). The **PyPI project `maintainability-agent`** is the closest open-source neighbour. It has 96 releases between 2026-05-11 and 2026-11-01, an MCP server, a `/maintainability-agent` Claude Code skill, and a grade it withholds "when evidence is thin". It is also **a naming collision with this repo's distribution name**, so publishing under that name is impossible and confusing even through git ([PyPI JSON](https://pypi.org/pypi/maintainability-agent/json)). Diff-based LLM reviewers (CodeRabbit, Copilot code review, Claude's `code-review` plugin) target bugs and compliance with standards. GitHub Code Quality adds LLM detection of maintainability problems on recently changed files but describes no rating scale ([GitHub Code Quality](https://docs.github.com/en/code-security/concepts/code-quality/code-quality)).

[Inference] The real gap is a combination that nobody ships. It has four parts: a Verdict for each of the five Characteristics (not one overall grade); an explicit `unknown` when the code cannot decide; Evidence for every pass or fail that points to file and line and traces back to a Measure; and published agreement and stability figures for those Verdicts. Each competitor covers at most two of the four. The gap is also closing: `quodeq` already does LLM grading per characteristic, and `maintainability-agent` already does deterministic grades that it calibrates itself. Positioning as "the first maintainability tool for Claude Code" would be false.

## Measures are well validated, but LLM Verdicts are not

The strongest direct evidence comes from Borg, Ezzouhri and Tornhill (ICSME 2024), who are affiliated with CodeScene. They benchmarked maintainability measures against 304 Java files, each rated by at least three experts. Their headline finding sobers any tool builder: **a plain size threshold (≤275 LoC) reached 0.91 accuracy and 0.95 AUC**. That is nearly identical to CodeScene Code Health (0.93 / 0.95) and a 33-feature AdaBoost model (0.92 / 0.97). The Maintainability Index scored 0.84. **SonarQube's technical-debt-ratio rating scored 0.61**, which led the authors to question earlier studies that used Sonar output as ground truth ([Borg et al. 2024](https://arxiv.org/html/2408.10754v1)). The same paper shows that **individual experts agree with the consensus only 70% of the time**, and that experts disagreed substantially on 17% of files. The underlying dataset (MainData, about 2,000 ratings from 70 developers on Java files) rates readability, understandability, complexity, modularisation and overall maintainability ([Schnappinger et al. 2020](https://www.researchgate.net/publication/345243028_Defining_a_Software_Maintainability_Dataset_Collecting_Aggregating_and_Analysing_Expert_Evaluations_of_Software_Maintainability)). Cognitive complexity, which the repo already computes through complexipy, has meta-analytic support. Across about 24,000 evaluations it correlates with comprehension time and subjective understandability, but the evidence is "mixed" for comprehension correctness ([Muñoz Barón et al. 2020](https://arxiv.org/abs/2007.12520)). Cyclomatic complexity correlates only moderately with size at the function level across 24 million functions, so it is "not shown to be redundant" ([Landman et al. 2016](https://ir.cwi.nl/pub/22662/)). [Inference] Every Verdict built on Measures must report size next to complexity, and the evaluation must show the tool beats a size-only baseline. Otherwise it adds nothing.

The SIG model is the published bridge from unit Measures to ratings for each Characteristic. Unit Measures fall into risk bands. The share of code in each band forms a "quality profile". A second set of thresholds turns each profile into 1–5 stars, calibrated so that 5/30/30/30/5% of benchmark systems get 1 to 5 stars ([Baggen et al. 2012](https://link.springer.com/doi/10.1007/s11219-011-9144-9)). The only publicly sourced low-risk thresholds found are **unit size ≤15 lines, McCabe ≤5 and ≤2 parameters** ([PyDriller Delta Maintainability docs](https://pydriller.readthedocs.io/en/latest/deltamaintainability.html), implementing [di Biase et al. 2019](https://doi.org/10.1109/TechDebt.2019.00030)). The cyclomatic-complexity bands reported for 2007 (1–10/11–20/21–50/>50) conflict with later SIG slides. The current SIG/TÜViT V15.0 thresholds sit in a guidance PDF that the research did not open ([SIG download page](https://www.softwareimprovementgroup.com/?p=24491)). [Inference] The rating layer needs its thresholds pinned to one primary source before code is written. The untracked `docs/agents/Maintainability_Measurement_Models.pdf` should be checked against V15.0. ISO/IEC 25010:2023 kept maintainability's five sub-characteristics unchanged. The 2023 changes were safety, interaction capability and flexibility ([ISO/IEC 25010:2023 preview](https://cdn.standards.iteh.ai/samples/78176/13ff8ea97048443f99318920757df124/ISO-IEC-25010-2023.pdf)). The glossary's five Characteristics therefore match the current edition. SIG still cites its basis as the 2011 edition. ISO/IEC 25023's measures for these Characteristics were not researched.

Evidence on LLM judgement is thin and mostly unfavourable. **No peer-reviewed study was found that compares a prompted LLM's maintainability Verdicts with expert ratings.** The nearest work uses cross-entropy from GPT-2 and Llama 2. It predicts maintainability only after controlling for logical lines of code, and without that control the relationship reverses ([Dillmann et al. 2024](https://arxiv.org/abs/2401.12714)). For readability, the closest analogue to analysability, ten LLMs correlated with humans at **r = 0.25 for Java and 0.02 for Python**. They rated 65% of snippets readable against 44% for humans. Prompting with a rubric raised coverage of aspects from 18% to 90% but did not improve agreement ([CoReEval](https://arxiv.org/html/2510.16579v1)). Determinism fails even at temperature 0: none of four models produced identical code reviews across five runs ([Klishevich et al. 2025](https://arxiv.org/abs/2502.20747v1)). Framing can flip verdicts on code smells **up to 72.57% of the time**, for example when a prompt says the code "already passed static analysis". A prompt that extracts evidence first lowers the best flip rate to 12.5% but does not remove the effect ([Fahad et al. 2026](https://arxiv.org/html/2607.10411v1)). These findings come from preprints using 7–8B models and older frontier models; none tested current Claude models. [Inference] An LLM-only Verdict would lean towards `pass`, drift between Runs, and bend to whatever the user claims. That is the case against "just asking Claude", and also the reason the hybrid design needs to be measured rather than assumed.

## Defensibility comes from code the model cannot overrule

The repo's current agent has neither a rubric nor access to Measures. Its whole system prompt is five sentences shared by all five Characteristics, described in its own docstring as "deliberately minimal and not tuned". **The agent has no Measure tool:** `measure_project` is called only from the CLI (`backend/src/maintainability_agent/agent/deep_agent.py:1-4, 28-34, 77-85`; `cli.py:47`). Today's Verdicts are therefore pure LLM judgement, the mode the evidence above warns against. Moving the same prompt into a Claude Code skill would produce something marginally worse than typing "rate the modularity of this repo" into Claude. [Inference]

[Inference] Seven properties would make the tool defensible, and each one is code or data rather than prompt text. First, Measures computed by our code and served through MCP, so the numbers are identical on every Run. Second, a SIG-style rating layer with thresholds as named constants that cite their source, so a `fail` follows a rule and a breach can be reproduced. The LLM's role shrinks to interpreting the rating, citing the worst units and choosing `unknown` when Measures cannot settle the Characteristic (reusability and modularity, for example, need structure that unit Measures do not capture). Third, Evidence validated by code: the existing `Finding` validator already rejects a pass or fail with no Evidence (`schemas.py:62-74`), and a second check can reject Evidence whose file or line range does not exist, or which cites no Measure. Fourth, a prompt that extracts Evidence before deciding and keeps user claims and lint status out, as the sycophancy study supports. Fifth, a separate rubric for each Characteristic that states which Measures and SIG properties feed it. Sixth, **published agreement with expert ratings and stability across Runs**, measured against three baselines: size only, Measures only, and LLM only. Seventh, open thresholds under a permissive licence, which Sonar, CodeScene and SIG do not offer.

The case against pivoting deserves a fair hearing. A university project is graded on its brief, not on market share. If the brief names DeepAgents or a web chat UI, the pivot fails regardless of its technical merit, and the repo audit found nothing that settles this. The market is crowded, the gap is closing, and a tool that only matches a size threshold adds nothing. Against that, the web chat path needs everything still missing: chat endpoints, a frontend, hosting, and LLM spend on the team's router. A plugin uses each user's own Claude and installs in two commands. [Inference] There is also a middle path that holds up either way. Build the core first, meaning Measures, the rating layer and the evaluation harness, with no dependency on any executor. Expose it through MCP so both a DeepAgents agent and Claude Code can call it. Delete the DeepAgents side only once the owner confirms the course allows it.

## A seven-phase plan that measures the old agent before deleting it

Everything in this section is the author's recommendation **[Inference]**. The only sourced parts are the constraints it cites: the repo rules (small single-topic PRs, Conventional Commits, the required check `lint-typecheck-test` kept by name, new dependencies justified and pinned, no comments in new code, `git rm` instead of `rm -rf`) and the audit facts.

### Eight decisions the owner makes before any code changes

**D1, course requirements:** does the brief require DeepAgents, LangGraph or a web UI, and what is the deadline? If DeepAgents is required, keep `agent/`, give it the MCP Measure tool, and skip Phase 6's removals. **D2, scope:** full replacement or a dual executor (DeepAgents and Claude Code over one core). **D3, name:** the PyPI name `maintainability-agent` is taken by an active project with the same pitch ([PyPI](https://pypi.org/project/maintainability-agent/)). Pick a distribution name, CLI command and kebab-case plugin name that does not start with `claude-` and is checked free on PyPI and the MCP registry, then rename the CLI entry point (`backend/pyproject.toml:20-21`). **D4, plugin location:** `.claude/skills/` is reserved for pinned third-party skills (`.claude/skills/README.md:3-5`), and `repo-structure.md` has no row for a plugin. The recommendation is a top-level `plugin/` folder holding `.claude-plugin/plugin.json`, `skills/`, `.mcp.json`, and later `agents/` and `hooks/`, with the repo root's `.claude-plugin/marketplace.json` pointing at `./plugin`. The server then launches as `uvx --from git+https://github.com/Group-Project-USTH/group-project@<tag>#subdirectory=backend <cli> mcp`. That this launch works from an installed plugin copy is unverified. The audit proved `uvx` only against a local `git+file://` URL, cold in 44 s. The alternatives are the whole repo as plugin (`source: "./"`) or a separate repo. **D5, distribution:** git and marketplace only, or PyPI as well. **D6, Langfuse:** the tracing adapter is a LangChain callback and cannot trace a Claude Code session (`observability.py:196-201`). Either keep it only for evaluation Runs driven by the harness or drop it. The `evaluate-characteristic` trace name feeds dashboards, so retire those deliberately. **D7, evaluation set:** MainData is Java only. The earlier research doc fixes the target language as Python (`docs/research/sonarqube-and-quantitative-measures.html:247`). Either hand-rate a Python set (who rates it, how many files, which Characteristics) or reopen the Python-only decision for a side study. **D8, threshold source:** the V15.0 SIG guidance or the course PDF, recorded in the ADR.

### How success is measured

Success is measured on the harness against expert ratings, with targets set from the literature rather than from intuition. **Agreement:** binary Verdict accuracy against the expert consensus per Characteristic. The bar is beating the size-only baseline, which reached 0.91 in Borg et al. Matching individual experts' 70% agreement with the consensus is a floor, not a goal. **Stability:** run each Characteristic five times per target and report the share of unanimous Verdicts and Fleiss' κ. The literature gives no threshold, so the ADR should set one; 90% unanimous is a suggestion. **Leniency:** compare the share of `pass` Verdicts with the experts' share, given the LLM bias of 65% against 44%. **Robustness to framing:** the flip rate when the prompt claims the code "passed static analysis". **Evidence validity:** 100% of cited files and lines exist, and every pass or fail cites a Measure. **Operations:** cold-install seconds, runtime dependency count, Measure wall time (1.85 s on the fixture today), and cost per Run in USD from `total_cost_usd`. Unit tests stay green throughout; they now pass 79 with 93% branch coverage, and `measures/` and `schemas.py` are at 100%. One gap remains open. No Python maintainability dataset rated by experts was found, so the harness's ground truth will be small and built by the team, and its findings should be reported with that caveat.

## Conclusion

The research changes the question. The question was "which framework should run the LLM". It is now "what does the LLM add on top of Measures". On the only expert-rated benchmark, lines of code alone almost matched the best commercial and ML predictors. LLMs rated readability more leniently than humans and barely in line with them. No study has tested an LLM that is given SIG-style ratings and asked for a Verdict per Characteristic with Evidence. For this project, Claude Code is a cheap, widely installed experimental platform for answering that question. That matters more than its role as a product channel. The deliverable worth defending is the agreement and stability table from Phase 4, not the plugin manifest.

The practical implication is that most of the work does not depend on the pivot. The rating layer, the missing SIG properties, Evidence backed by Measures and the evaluation harness are needed whether Verdicts come from DeepAgents or Claude Code. These phases can start as soon as the ADR is merged, even while the course question (D1) is open. The PyPI name collision is the one decision that cannot wait. Every published artifact (plugin name, CLI, marketplace entry) inherits it, and the other project's name already belongs to a product with an almost identical pitch.
